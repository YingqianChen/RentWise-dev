## 已解决的问题

| 问题 | 实现方案 | 验证结果 |
| --- | --- | --- |
| 用户确认金额后没有冻结计费周期；重新分析可能借用新周期 | 管理费和差饷分别保存金额及月/季/年/未知周期；确认时冻结当前周期，修正时显式选择；审计保存前后周期 | 季度 600 管理费和 900 差饷加月租 18000，月成本为 18500；新来源改成月付后仍保留用户确认的季度单位 |
| 用户必须自行把季费换算为月费，容易填错 | 编辑框直接输入原报价及周期，后台统一换算；页面显示采用的周期及与最新来源的差异 | 900 年费换算为每月 75；浏览器覆盖 900 季费修正；未知周期不猜、不当作零 |
| 管理费的季度/年度周期未参与月成本计算 | 两类费用复用周期处理，从各自明确证据读取，避免借用月租或其他费用的单位 | 数值千位逗号、英文前置周期、混合条款及周期未知场景通过 |
| 模型抽取出的数字出现在引文里，但引文实际是外币、范围或负数 | 此类金额证据降为推断，避免直接进入可信金额计算；拒绝超大整数避免验证器溢出 | USD/US$、负数、范围、2000 位整数回归通过 |
| 数据库删除已完成，磁盘删除失败会留下无法追踪的截图 | 在删除记录的同一事务中保存清理任务；提交后尝试删除，失败以退避方式重试，成功后移除任务 | 文件系统 PermissionError 不破坏已完成的删除；新 worker 能重新读取任务并完成清理；业务回滚同时撤销清理意图 |
| 多个 worker 可能重复领取任务；不同本地磁盘可能把缺失文件误判为已清理 | PostgreSQL 行锁及 SKIP LOCKED；上传卷保存持久 UUID，worker 只处理同一卷的任务 | 两个并发 worker 只领取一次；其他上传卷不会领取已到期任务；16 个并发初始化得到同一卷 UUID |

## 数据迁移与运行要求

- 新增 `20260909_0018`（费用周期/审计）、`20260909_0019`（文件清理任务），承接 `0017` 请求额度表。部署前备份并按正常迁移流程升级至 head；目前只应用于独立 `rentwise_review_test`，迁移回退/升级回归通过。不要用 `stamp head` 跳过缺失的表和字段。
- 老的人工修正遵循原 API 的“每月等值”约定；老的人工确认没有保存单位，保守显示周期未知，需重新确认或修正。没有凭后来证据回填历史单位。
- 非 test 环境的应用 lifespan 每 30 秒处理最多 25 个到期清理任务。每项失败按 30 秒至 1 小时退避；不调用模型。失败只记录异常类别，不记录上传内容。
- `LOCAL_UPLOAD_ROOT` 必须是持续可用的正确上传卷。`.rentwise-storage-id` 与上传文件共同保留、备份和恢复；不能随意删除或替换。此实现需要文件系统支持同目录硬链接来原子初始化卷标识。错误或不支持的存储应先修复，不能忽略任务后当作已经删除。
- 从 backend 可运行 `python -m scripts.process_file_cleanup` 处理本卷已经到期、已经授权的清理任务。它不扫描历史孤儿文件，也不会绕过重试等待时间。
